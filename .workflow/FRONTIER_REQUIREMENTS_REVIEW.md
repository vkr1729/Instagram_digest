# Frontier Requirements Review — Cookie-Free Anonymous Pipeline Toggle

## 0. Scale Anchor (non-negotiable)
- Target: single-user personal CLI / weekly cron. No multi-tenant DB, no microservices, no auth server, no per-account state machine.
- Control surface stays minimal: one bool (`COOKIE_FREE_MODE` in `config.py`, env-read, default `False`) + two CLI flags (`--cookie-free` / `--use-cookies`, CLI wins, neither → config). Log resolved mode at startup.
- Terminology fix: REQUIREMENTS.md §2 says "skip loading `session.json`" — no such file exists. Cookie state is `data/cookies.json` (Playwright/requests) + `cookies.txt` (yt-dlp) + implicit `--cookies-from-browser chrome` fallback. Spec should name these.

## Q1. What does "anonymous failure" mean — skip, backoff, or abort?
- **Ambiguity / failure mode:** Logged-out Playwright hits login walls (`/accounts/login`), empty reels grids, and IP-based 429s far more often than authenticated runs. REQUIREMENTS.md says "exponential backoff or gracefully proceed" — those are opposite strategies. Current code treats `InstagramBlocked/Challenged` as instant-abort-with-alert (correct for a gated *account*, wrong for anonymous where there is no account to protect). Reusing that path in cookie-free mode would abort every run and fire meaningless cookie-alert emails/popups.
- **Recommended:** Cookie-free failures are soft by default: per-creator skip, continue roster, then apply the existing viability gate (`MIN_CANDIDATE_RATIO`, `MAX_EMPTY_CREATOR_RATIO`) and the `MIN_DEPLOY_ITEMS` (150) shortfall gate. Never trip the account-safety `_GATE` for anonymous 429/empty-grid (there is no account to protect); never send cookie-alert email or `raise_cookie_attention` popup in this mode. Bounded per-creator retry only (e.g. 1 retry), no 20+40+80-min sleeps — a single-user cron run must finish overnight, not sleep through it.
- **Alternatives:** (a) Full reuse of authenticated backoff (20/40/80 min) — simple but turns every anonymous rate-limit into a multi-hour stall. (b) Hard abort on first login wall — predictable but a single private/deleted creator kills the week.

## Q2. How do mode mismatches across resume/checkpoint/cron resolve?
- **Ambiguity / failure mode:** Sync checkpoints (`sync_progress_*.json`), `candidates_cache.json`, banked `ranked`/`enriched` lists, and cron env (`run_weekly.sh`, `resume_pending.sh`) can straddle modes: a cookie run banks work, the retry runs `--cookie-free`, or cron inherits a stale `COOKIE_FREE_MODE` export. REQUIREMENTS.md defines invocation precedence but not checkpoint precedence. Silent mode-mixing produces unreproducible digests (e.g. half media-API-enriched, half anonymous).
- **Recommended:** Stamp `cookie_free: bool` into every sync checkpoint + candidates cache; on load, if banked mode ≠ resolved mode, log loudly and refuse to mix unless `--force` (fresh start) or `--resume` explicitly adopts banked mode. Keep precedence: CLI flag > `COOKIE_FREE_MODE` env > default `False`. Single log line at startup: `mode=cookie-free (source: --cookie-free)`.
- **Alternatives:** (a) Always allow mixed resume (max reuse, but metadata quality becomes inconsistent — see Q4). (b) Separate checkpoint namespaces per mode (`sync_progress_<week>_anon.json`) — avoids refusal logic but doubles resume/cleanup paths for a single-user tool; reject as overhead.

## Q3. Which code paths actually touch identity, and how are they all gated?
- **Ambiguity / failure mode:** Cookies leak through at least six paths, not just "session init": `InstagramSession._inject_cookies()` (reads `cookies.json`), `get_cookie_args()` (falls back to `--cookies-from-browser chrome` — an identity leak that silently defeats "permanent cookie-free"), `fetch_media_info_batch` (requires `sessionid`), `sync_following_accounts` (following API + `cookie_exporter.py` subprocess), `_ensure_valid_session`/`_probe_session_once` + follow-cooldown/.py, and yt-dlp metadata/download fallbacks invoked with cookie args. Missing any one breaks the anonymity guarantee while appearing to work.
- **Recommended:** One central predicate (e.g. `config.is_cookie_free()` / resolved flag threaded from `main.py`) gating all of them: `_inject_cookies` no-op, `get_cookie_args()` returns `[]`, media-API path skipped entirely, `--sync-following` refused with a clear error in cookie-free mode, probe/validation/cooldown/cookie-exporter bypassed, yt-dlp always invoked cookie-less, `extract_external_reels_from_feed` never called (Tier 3 skipped per spec). Add one regression test asserting no cookie file read / no `--cookies-from-browser` arg construction when the flag is on.
- **Alternatives:** (a) Scattered `if` checks per call site — works initially, rots fast. (b) Separate anonymous extractor module — clean isolation but duplicates ~2000 lines of Playwright logic for one user; reject.

## Q4. What is the metadata-quality contract when anonymous pages degrade?
- **Ambiguity / failure mode:** The pipeline assumes authenticated-quality metadata: `<time datetime>`, `og:description` likes/comments, `video_versions` CDN URLs, and the `media/{id}/info/` API (which needs `sessionid` and is therefore *unavailable* anonymous). Logged-out pages frequently omit timestamps, hide like counts, and withhold progressive `.fbcdn.net` URLs. Downstream, `cutoff_ts` filtering drops timestamp-less reels, ranker scoring starves without likes/views, and Phase 5A downloads fail without a CDN URL. REQUIREMENTS.md promises "remainder operates identically" — it cannot, because inputs are poorer.
- **Recommended:** Define the degradation explicitly: media-API prefilter disabled in cookie-free mode; timestamp-missing reels are dropped by the same cutoff rule (no silent stale admission — keeps the "finite weekly briefing" promise); `metrics_estimated=True` is expected and ranker falls back to grid view-counts; reels with no resolvable CDN URL after Playwright + cookie-less yt-dlp are dropped at download stage (counted toward shortfall, not retried forever). Document that anonymous digests skew toward grid-visible view counts rather than exact likes.
- **Alternatives:** (a) Lenient cutoff (admit dateless reels) — fills quota but admits stale content, breaking the weekly contract. (b) Attempt unauthenticated `media/info/` calls — adds code for an endpoint that requires auth; reject after one probe.

## Q5. Who fills the Tier 3 quota, and what happens below 150?
- **Ambiguity / failure mode:** Skipping Tier 3 feed top-up removes up to 40% (`MAX_EXTERNAL_SHARE`) of digest capacity. REQUIREMENTS.md says "expanding creator channel depth or completing with available banked candidates ≥ MIN_DEPLOY_ITEMS" — but channel depth is currently capped (5/creator, 6 food, 8 recommended, `MAX_PER_CREATOR=4` in final ranking) and the shortfall gate aborts below 150 without touching R2. An anonymous run with thinner per-creator yields can pass viability yet fail deploy with no recovery path specified.
- **Recommended:** Compensate in order: (1) raise anonymous discovery depth (more reels per creator tab scroll) before widening the roster; (2) keep `MIN_DEPLOY_ITEMS=150` hard — below it, checkpoint as `shortfall_paused` (same mechanism, no R2 mutation, no digest overwrite) for a later `--use-cookies` resume rather than deploying a thin digest or auto-lowering the bar. Never auto-deploy partial weeks; single-user trust in the archive matters more than quota-filling.
- **Alternatives:** (a) Anonymous hashtag/explore pseudo-feed as Tier 3 replacement (spec explicitly rejected — keep rejected; it reintroduces feed-scrape risk with worse signal). (b) Lower `MIN_DEPLOY_ITEMS` in cookie-free mode — hides the shortfall instead of preserving it; reject.
